# Recall relevance — offline prototype, 2026-10-21

**Verdict: usable technical prototype; NOT a validated post-VCC retrieval system.**
The real replays are partial. Do not select a production block size, claim a
retrieval win, or activate a hook from these measurements.

## Authorization and checkpoints

User explicitly authorized blocks 0–3: source contract, CPU extraction, local
scoring and offline replay. No production integration, server restart/cache
reconfiguration, transcript upload, push or publication was authorized or done.

- `fd74963`: canonical snapshot bridge and lossless segmentation.
- `8a629a9`: local bounded scorer and independent HTTP/math tests.
- `0bf5d51`: closed metric-path allowlist after independent leak reproduction.
- `2610c20`: offline CLI, frozen annotations, partial-coverage evaluation and
  experimental raw-prefix anchor probe.

The implementation is source-checkout-only; it is not a new installed Pi tool.
The existing extension, vendor protocol, package manifest and production
configuration are unchanged relative to `757b4e0`.

## What is actually demonstrated

1. Canonical Pi before/after projection plus installed VCC global indexing;
   abandoned branches, exclusive keep boundary, edits and two compactions tested.
2. All admissible source text is segmented, including plaintext thoughts.
   Thoughts/full arguments/projected replacements use a **separate private
   manifest consultation**, not an invented capability of `vcc_recall expand`.
3. Local-only JEV binary scoring: existing renderer/policy, A=no/B=yes, native
   top-20 logprobs, FP32 two-label softmax, exact final-prompt token ceiling.
4. Loopback literals only; direct sockets ignore proxy settings; no redirect,
   hosted fallback, retry loop, raw prompt logging or automatic source injection.
5. Global per-run deadline, explicit failed/not-attempted rows, null unscored
   probabilities. Closed metadata paths prevent backend numeric keys from
   echoing arbitrary source fragments into score artifacts.
6. Annotation files are bound before inference and checked again afterward.
   Evaluation checks their exact source spans and hashes, not model self-grades.

## Real scoring: cost and cache are the blocker

### Initial 2K smoke, case A

- 60 s campaign, at most 8 candidates, spread schedule over the whole zone.
- **3/140 scored**, one timed out during scoring; remaining rows explicitly
  not attempted. Unique source coverage: **2.09%**.
- Prompts: 29,311 / 29,712 / 29,776 actual tokens.
- Their server prefill times: **16.61 / 17.09 / 16.92 s**.
- Each reports `cache_n=0` despite a logically common current-context prefix.

A shared prefix in the prompt is therefore **not evidence of effective reuse**.

### One-prefix-anchor experiments

The probe adds one raw completion of the common prefix, discards that output,
and then sends the **unchanged candidate prompts**. No runtime flags change.

1. Repeating the first three already-scored candidates completed in 8.09 s
   including the anchor. Their prompt hashes and scores were identical to the
   original three (score delta 0). They reused their own nearly full previous
   endpoints. **This is NOT proof that the anchor accelerates unseen candidates.**
2. Extending to additional candidates, with a 60 s common budget, scored
   **7/140** (4.79% unique source coverage). The first additional completed
   candidate reused **27,627 tokens**, evaluating a 3,280-token suffix in
   2.10 s. **It had already been submitted in the interrupted smoke**, with
   the same prompt hash; it is not an unseen-candidate cache proof.
   The following three candidates, not submitted in that smoke, each reported
   **zero reuse** and **16.56 / 16.91 / 16.54 s** of prefill. The eighth timed out.

**The one-anchor arrangement does not establish durable reuse on this active
server.** Eviction, retention policy and other-client interference are possible
explanations, not verified causes. Do not tune the server under the current GO.
These are ordered diagnostic runs, not a randomized cold-cache A/B benchmark.

## Quality evaluation and omissions

Annotations were frozen before the first relevance score: four hypotheses in A
(two marked critical), three useful hypotheses in B. Their labels are hypotheses
about helpful consultation, not proof of causal necessity or an exhaustive truth
set. Consultation ceiling: **8,000 estimated tokens**, shared by all methods.

Methods: JEV rank, recency, chronological control and a **digest-shaped pointer
control**. Every method uses the same actually scored pool; unscored blocks are
not assigned probability zero. The pointer control is recomputed on the
canonical zone: **it is not the exact shipped/delivered digest baseline**.

- In the small A pools, JEV and recency both cover the same **1/4 annotation**.
  Often the whole tiny pool fits under 8K, so this is not a discriminating test.
- Both critical A annotations and the other useful A annotation are **not fully
  in the scored pool**. They were missed at scoring coverage, not demonstrated
  irrelevant by the model.
- In B, **none of the three annotations is fully in the scored pool**; every
  method covers 0/3. Again this cannot compare ranking quality.
- Selected source-span overlap is reported separately from prompt/header cost.
  The spread schedule happened to select nonoverlapping source spans in these
  small pools; this does not mean full-zone overlap is zero (see extraction).
- Reports retain all omission causes, annotation-level miss causes, unique text
  coverage and selected consultation cost. No critical omission is called a
  successful retrieval.

### Synthetic directional smoke

A non-private synthetic fixture was written **before inference**: relevant authorization
constraint, source-access correction, rejected-layout rationale, unrelated soup
recipe. Same fixed question and renderer; one 30 s campaign, four rows complete.
Scores: **0.9972 / 0.9968 / 0.9975 / 0.00247**. All three useful controls outrank
the unrelated one as expected. This is a directional smoke, not calibration or
proof of general retrieval quality. See `tests/fixtures/recall_relevance_controls.json`.

## Remaining gates / safe stopping point

- Blocks 0/1: implemented and verified.
- Block 2: scorer works and controls pass; real full-zone cache/cost feasibility
  is not established. One raw-prefix anchor is not a validated solution.
- Block 3: machinery exists; real replay is explicitly **partial**. Full 1K/2K/4K
  equal-budget quality comparison and final held-out validation remain open.
- Blocks 4/5: no integration decision or activation. Existing memory scoring,
  cold start and tool are untouched.

**Next technical question:** how can the fixed current-context prefix remain
reusable throughout a campaign on the unchanged active runtime? Diagnose with
read-only cache evidence and a tightly controlled experiment before expanding
runs. A different client layout or reduced current-context view would need its
own fidelity/score comparison; a runtime change needs a separate GO. Simply
raising a timeout does not establish an acceptable post-VCC latency.
